# Enforce the compiled-file mode unconditionally via explicit chmod

Compiled files derived from an `age`-encrypted source must be `0600`; all other compiled files are `0644` (the compile dir itself is `0700`). `writeCompiledFile` (in `internal/compiler/compile.go`) chose the right `perm` and passed it to `os.WriteFile`, but `os.WriteFile` only applies its mode when it *creates* the file — for an existing file it truncates and rewrites content while leaving the old mode untouched. The content-hash idempotency early-return also returned before any permission logic ran. So if a destination already existed at `0644` (a target previously shipped as a plaintext fragment and later switched to a `.age` source compiling to the same relpath, or a file left by an older run / other tooling / a permissive umask), a later compile wrote the decrypted secret into it and left it `0644`. We now compute the intended mode once (`compiledFileMode`) and `os.Chmod` to it explicitly on every path: the fresh/changed write, and — for `FromEncrypted` files — the content-unchanged idempotent re-run. `WriteCompiled` additionally chmods the compile dir to `0700` after `MkdirAll`, because `MkdirAll` does not tighten a pre-existing directory.

This is recorded because the `0600` and `0700` guarantees are documented (README, PRD) but were enforced only on the create path, and the gap is non-obvious: `os.WriteFile(path, content, 0o600)` reads as if it always sets the mode. A future contributor could reintroduce the bug by routing a write through `os.WriteFile` alone, or by "simplifying" the idempotent-path chmod away on the grounds that an unchanged file "doesn't need rewriting" — which is exactly the path that must repair a stale mode. The impact was **LOW**: the compile dir is `0700` out of the box, so a `0644` file inside it is not readable by other local users; disclosure required a non-default loose compile dir (or ancestor). But it was a silent violation of the documented guarantee and a latent risk if perms later loosened, so the enforcement is made explicit and independent of create-vs-truncate.

## Considered Options

- **Compute the mode once and `os.Chmod` on every write path, including the idempotent early-return for encrypted files (chosen)** — makes the `0600`/`0644` guarantee hold regardless of whether the destination pre-existed or its content changed. Chmod is colocated with each return, so the invariant cannot be read past, and the idempotent path still avoids the content rewrite while repairing the mode.
- **Pre-delete an existing destination before writing so `os.WriteFile` creates it fresh** — rejected: a remove+create widens the window where the file is absent, loses the cheap content-unchanged short-circuit, and is more error-prone than a single chmod for the same guarantee.
- **Chmod only on the write path, not the idempotent early-return** — rejected: the content-unchanged re-run is precisely the case the original bug report reproduced (a pre-existing file with matching content but a stale `0644` mode). Skipping it would leave the guarantee broken on the most common repeat-compile path.
- **Document the guarantee and rely on the create-time perm** — rejected: that is the state that produced the bug. The mode must be enforced at the sink, not assumed from `os.WriteFile`'s create-only behaviour.

## Consequences

- A compiled file from an encrypted source is `0600` after every compile — fresh write over a pre-existing `0644`, content-changed re-write, and content-unchanged idempotent re-run alike. Non-encrypted compiled files are `0644` on the write paths the same way.
- A pre-existing, loosely permissioned compile dir (e.g. `0755` from an older run, which `MkdirAll` leaves untouched) is tightened back to `0700` on the next `WriteCompiled`, closing the actual disclosure gate.
- The idempotent re-run is no longer a pure no-op for `FromEncrypted` files: it still skips the content rewrite but issues a chmod to repair a stale mode. Dry-run still performs no filesystem writes.
- `compiledFileMode` is the single place the `0600`/`0644` choice is made; the write path and the idempotent-repair path must keep deriving the mode from it so they cannot drift apart.
